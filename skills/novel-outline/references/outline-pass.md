# 骨架 · 砍線 / 合人 / 排爽點

拿全部卷摘要（或短篇原文）+ 使用者參數，產出 outline.json 的**骨架四塊**：`adaptation` / `characters` / `scenes` / `beats`。分集梗概**這一步不寫**——骨架沒拍板就寫分集，方向錯了全廢。

## 順序就是方法

1. **砍線**。短劇只裝得下一條主線 + 至多一條副線。砍掉的寫進 `adaptation.cut`，每條都要有 why。`adaptMode` 不是忠實時一條不砍會被 validate 攔。
2. **合人**。功能重複的角色合成一張臉（兩個報信的 → 一個），合併進 `characters[].from` 的 ← 改動記錄。然後**分檔**（`tier`）：主角組 `lead` 1–5 人、有名字的重要配角 `support` ≤ 10、功能性角色 `functional` ≤ 10。功能性角色佔臉不佔名——`name` 用稱呼標籤（「急診醫生」），也不用寫人物弧。無名背景人不進表。
3. **收場景**。主場景上限隨集數走（4 + ⌈集數/10⌉，夾在 5–15：6 集給 5 個，60 集給 10 個），以 `validate` 報的數為準。這是 AI 短劇的寬鬆版——場景是生成的，多開幾個景換觀賞性是划算的，別把戲都憋在一個屋裡。原著裡只出現一次的場景，要麼砍掉、要麼寫 `reusePlan`（複用哪個現有環境資產、換什麼時段天氣改出來）。
4. **排爽點**。先定 major（大爆點）落在哪幾集，再拿 minor 填縫。硬規則：相鄰間隔 ≤ 3 集、開頭結尾無真空、最早的 major 不能在最後一集。`type` 跟著題材走——女頻打臉和男頻戰神的爽點不是一種東西，看 `params.genre`。
5. **收道具**。**排在爽點之後不是隨便排的**——敘事道具的判據是「它托起哪個爽點」，爽點沒定就分不清哪件物件是道具、哪件只是陳設。上限 8 件，跟主角數量一個量級。每件寫 `function`（它在戲裡承載什麼）與 `beatIds`（托起哪幾個爽點），分集用 `propIds` 引用。

   **一件東西該不該進這張表，問一句就夠了：它壞了、丟了、被換掉，劇情會不會塌。** 會塌就是敘事道具（皮箱、硯臺、那封信）；不會塌就是場景陳設（船艙的掛燈、桌上的茶碗），歸 `novel-art` 的場景錨點管，不進這張表。填不出 `function` 的一律不收——**填不出來的不是道具，是背景**。

每一步都基於卷摘要裡的原料。**關鍵取捨在 `adaptation.keep` 裡附 `evidence`（原文逐字片段）**——大綱要能指回原文，不是憑印象改編。

砍完、合完之後各補一句結論：`adaptation.cutNote` 寫砍線的含義（「這意味著：全劇終點是……」），`adaptation.mergeNote` 寫主角組入選理由（誰有完整轉變弧）。這兩句會出現在報告最前面的「關鍵決策」區塊，也是拍板時給使用者看的核心內容。

## 兩輪規則 ⛔

骨架必須跑兩輪：

- **第一輪快版**：四塊填齊、能過 `validate --stage beats` 就停，**交給使用者拍板**。砍了哪條線、合了哪些人、大爆點在第幾集——這三件事使用者不點頭，後面全是白乾。
- **第二輪細版**：吸收使用者意見後細化，再過一次 `validate --stage beats`。

快版的意義是便宜——錯了只損失一輪骨架，不是 60 集梗概。

## 自檢

寫完跑：

```bash
node scripts/novel-outline.mjs validate <outline.json> --stage beats
```

有違規逐條修，改完重跑，直到通過才允許進分集。
